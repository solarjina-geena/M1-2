# M1-2 발표용 핵심 개념 정리

발표 때 화면과 함께 짧게 설명할 수 있도록 프로젝트 기준으로 정리했다.

## 1. 시계열 데이터에서 AI 답변까지

**한 문장:** 날짜와 공정별 생산 기록을 정리해 통계와 추세를 계산하고, 그 요약과 관련 근거를 AI에 전달해 답변을 만든다.

1. Firestore `data` 컬렉션에서 제조 기록을 읽는다.
2. 생산수량 수치가 있는 기록을 날짜와 생산 RUN 순서로 정렬한다. 빈칸은 0으로 바꾸지 않는다.
3. 서버가 건수·기간·합계·평균·최대·최소를 계산한다. 현재 배포 요약은 전체 1,086건 중 수량 기록 250건이다.
4. 추세는 정렬된 마지막 구간 평균과 그 직전 구간 평균을 비교한다. 변화가 +2% 초과면 증가, -2% 미만이면 감소, 그 사이는 유지로 표시한다.
5. 질문에 관련된 제조 기록과 요약을 시스템 지침에 넣어 AI에 보내고, 답과 제공자 정보를 대화로 저장한다.

현재 배포 캡처는 `docs/screenshots/chat-firestore-codyssey-2026-10-27.png`이며 Codyssey 추가 분석 표시가 보인다. `seed-demo`의 평가용 합성 120건은 Firestore의 기존 제조기록과 별개다.

## 2. FastAPI의 라우터·서비스 계층을 왜 나누나

**한 문장:** URL 처리, 업무 규칙, 데이터 저장을 나누면 각 역할을 찾고 바꿀 때 서로 덜 영향을 준다.

- 라우터: HTTP 경로와 요청·응답을 처리한다.
- 서비스: 요약·분석 등 업무 규칙을 실행한다.
- 스키마: Pydantic으로 입력 형식과 범위를 검증한다.
- 저장소: Firestore 읽기·쓰기와 캐시를 담당한다.

현재 프로젝트의 FastAPI 코드는 `backend/app/main.py`에 많이 모여 있어 계층 분리는 개선 과제로 남아 있다. 발표에서는 현재 구조와 분리했을 때의 장점을 구분해 설명한다.

## 3. Pydantic 입력 검증

**한 문장:** 잘못된 날짜·숫자·필드가 저장 로직에 들어가기 전에 요청 단계에서 거절한다.

예를 들어 날짜가 실제 달력 날짜인지, 생산수량이 유한한 숫자인지, 모델이 IV·OV·HSV 중 하나인지 확인하고, 오류에는 HTTP 422를 돌려준다. 채팅 질문도 비어 있지 않고 2,000자 이하인지 검사한다.

## 4. Firestore 컬렉션과 CRUD

**한 문장:** 컬렉션은 종류별 문서 묶음이고, 각 문서는 고유 ID로 조회·수정·삭제한다.

- `data`: 생산·품질 기록 문서
- `conversations`: 제목, 문맥, 질문·답변 메시지
- `reviews`: 사람의 검토·정정 기록

CRUD는 Create(추가), Read(조회), Update(수정), Delete(삭제)다. 화면 증빙은 `data-crud-create.png`, `data-crud-update.png`, `data-crud-delete-restored.png`에 있다.

## 5. 컨텍스트 주입

**한 문장:** AI가 추측하지 않도록 현재 데이터에서 계산한 요약과 질문에 관련된 근거를 프롬프트에 함께 넣는다.

AI에게 전달된 자료에 없는 원인이나 수치를 만들어내지 않도록 지시한다. BA와 CA처럼 이어지는 공정의 생산량을 합산해 전체 생산량이라고 부르지 않으며, 확인값과 계산값도 구별한다.

## 6. Render·Vercel 환경변수, CORS, 키 보호

**한 문장:** 서버 비밀키는 Render에만 보관하고, Vercel 브라우저에는 공개 가능한 Render API 주소만 둔다.

- Render: Firestore 서비스 계정, AI 키, 관리자 토큰 등 서버 비밀 설정
- Vercel: 정적 Vanilla 화면과 공개 가능한 `API_BASE_URL`
- CORS: 브라우저 출처가 허용된 API 도메인에만 요청하도록 제한
- 키 보호: 키는 프론트엔드 코드·Git·스크린샷·보고서에 기록하지 않는다.
